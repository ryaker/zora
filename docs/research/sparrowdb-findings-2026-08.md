# SparrowDB — Bug & Enhancement Report

**For:** the SparrowDB maintainers / a SparrowDB-focused coding agent
**From:** Zora integration work (MEM-30), August 2026
**Version tested:** `sparrowdb@0.1.21` from npm
**Environment:** Linux x64 (glibc), Node v22.22.2, prebuilt `@sparrowdb/linux-x64-gnu`

Everything below is **empirically reproduced**, not inferred from docs. The probe
scripts that produced these results are checked in alongside this file
(`sparrowdb-probe.mjs`, `sparrowdb-probe2.mjs`) and are written so they can be
adopted directly as a regression suite — each case is a one-liner with an
expected result.

Findings are ordered by severity. Suggested fixes are offered as starting points,
not prescriptions — the maintainer knows the internals.

---

## S0 — Cypher injection is possible by construction

**The single most important item in this report.**

There is no parameterized-query API. `execute(cypher: string)` takes a string and
nothing else, so every caller must build Cypher by interpolation, and every
caller must therefore write their own escaper. At least one interpolation vector
is exploitable today.

### Repro 1 — property injection

```js
const evil = '", role: "admin';
db.execute(`CREATE (:User {name: "${evil}"})`);
db.execute('MATCH (n:User) RETURN n.name, n.role');
```

**Actual:** `{ "n.name": "", "n.role": "admin" }` — the attacker-controlled string
closed the `name` value and added an entirely new property.
**Expected:** a `User` node whose `name` is the literal string `", role: "admin`.

### Repro 2 — WHERE-clause filter subversion

```js
const evil = '" OR n.name <> "';
db.execute(`MATCH (n:User) WHERE n.name = "${evil}" RETURN n.name`);
```

**Actual:** returns rows — the predicate was rewritten by the input.
**Expected:** zero rows (no node has that literal name).

### What currently *does* block escalation (and why it isn't a defense)

Two parser limitations happen to stop the worst cases:

```js
db.execute(`CREATE (:Note {body: "${'"}) CREATE (:Pwned {x: "1'}"})`);
// → invalid argument: unexpected trailing token: Create      (:Pwned count stays 0)
```

Statement-chaining is blocked only because **multiple clauses in one statement
are unsupported** (see S2-1). That is an accident of incompleteness, not a
security boundary — the day multi-clause statements are implemented, this becomes
arbitrary graph mutation. Please don't treat the current behaviour as safe.

### Why this matters beyond Zora

Any consumer feeding user- or LLM-generated text into the graph has this hole.
In Zora specifically, node properties come from memory summaries that are
generated by a model reading tool output — i.e. content an attacker can influence
through a web page or a file. That's the classic path from prompt injection to
data-store compromise.

### Suggested fix

Add parameter binding as a first-class API, and make it the documented path:

```ts
execute(cypher: string, params?: Record<string, Value>): QueryResult
// db.execute('MATCH (n:Person {name: $name}) RETURN n.name', { name: userInput })
```

Bind at the AST/plan level so values never re-enter the parser. Two sub-notes:

- **`$name` is currently accepted and silently ignored** — see S1-1, which is a
  correctness bug in its own right and will become a footgun the moment binding
  ships if the syntax isn't reserved now.
- If full binding is a large change, an interim `SparrowDB.escape(value)` /
  `sparrow.literal\`...\`` tagged template in the official bindings would at
  least give consumers one audited escaper instead of N hand-rolled ones.

## S1 — Correctness

### S1-1. `$param` placeholders are silently ignored, dropping the filter

```js
db.execute('MATCH (n:Person {name: $name}) RETURN n.name');            // no params at all
db.execute('MATCH (n:Person {name: $name}) RETURN n.name', {name:'Alice'});
```

**Actual (both):** returns **every** `Person` — Alice *and* Bob2.
**Expected:** an error (`unknown parameter $name`), or correct filtering when
bound.

This is the worst failure mode available: not an error, not zero rows, but a
**silently unfiltered result set**. A caller who believes they are filtering gets
the whole label back. If that result then drives a delete or an authorization
decision, the consequences are severe.

Note the second call passes a params object; `index.d.ts` declares
`execute(cypher: string)` so TypeScript rejects it, but plain-JS callers get
silent wrong answers.

**Fix:** reject unknown/unbound parameters with a clear error, even before
binding is implemented.

### S1-2. `RETURN n` (whole node) returns hashed column names, losing property names

```js
db.execute('CREATE (:M {a: 1})');
db.execute('MATCH (n:M) RETURN n');
```

**Actual:** `{ "n": { "col_3826002220": 1 } }`
**Expected (per `index.d.ts`):** `{ "n": { "$type": "node", "id": "<u64 string>" } }`

Two problems in one:

1. **Property names are replaced by what look like hashed key ids**, so a
   returned node is unusable — you cannot map `col_3826002220` back to `a`.
2. **It contradicts the published types.** `index.d.ts` documents `NodeRef` as
   `{ $type: 'node', id: string }` with a careful explanation about u64 precision.
   No `NodeRef` is ever produced. Same for `EdgeRef` — I could not get one out of
   any query.

Consequence for consumers: you must enumerate properties explicitly
(`RETURN n.a, n.b`) and can never round-trip a node. That's a significant
ergonomic and capability gap, and the type mismatch means TypeScript users write
code against a shape that never arrives.

**Fix:** decide which contract is intended and make the other match it. Returning
real property names in a map would be the most useful; returning the documented
`NodeRef` would at least be honest.

### S1-3. Booleans round-trip as integers

```js
db.execute('CREATE (:B {flag: true, other: false})');
db.execute('MATCH (n:B) RETURN n.flag, n.other');
```

**Actual:** `{ "n.flag": 1, "n.other": 0 }`
**Expected:** `{ "n.flag": true, "n.other": false }`

`WHERE n.flag = true` does match, so storage/filtering is fine — it's the
result-marshalling that loses the type. `Value` in `index.d.ts` includes
`boolean`, so this contradicts the declared type. It also makes booleans
indistinguishable from `0`/`1` integers on read.

### S1-4. Unknown functions return `null` instead of erroring

```js
db.execute('MATCH (n) RETURN nosuchfn(n)');
// → one row per node, all null. No error.
```

A typo'd function name silently yields nulls. Should be a parse/plan error.

## S2 — Cypher coverage gaps

Each of these is a legitimate "not implemented yet"; they're grouped here because
each one forces a workaround on consumers, and several **contradict the shipped
documentation**, which is the more actionable half.

| Query | Result | Notes |
|---|---|---|
| `CREATE (...) CREATE (...)` (multi-clause) | `unexpected trailing token: Create` | Forces one round-trip per node. Also the accidental injection guard (S0). |
| `MATCH (a)-[r:KNOWS]->(b) SET r.strength = 0.9` | `MATCH...SET/DELETE currently supports only single-node patterns (no relationships)` | **Edge properties can never be modified after creation.** Consumers must delete and recreate edges. Biggest practical gap for a mutable knowledge graph. |
| `MATCH (n) DETACH DELETE n` | `unexpected token after MATCH pattern: Detach` | No way to delete a connected node without manually removing edges — and edges can't be individually deleted either (same single-node restriction). Risk of orphan edges. |
| `MATCH (n) REMOVE n.prop` | `unexpected token after MATCH pattern: Ident("REMOVE")` | No property removal. |
| `RETURN DISTINCT type(r)` | **`not found`** | Two issues: DISTINCT appears unsupported, and the error text is uninformative (see S3-1). The bundled skill docs list this exact query as supported. |
| `MATCH (a)-[*1..3]->(b)` | `variable-length paths require a relationship type: use [:R*] not [*]` | Good error. But the bundled skill docs show `[*1..3]` as a working example. |
| `CREATE (:T {n: null})` | `CREATE property 'n' is null; use a concrete value` | Reasonable, but means optional fields must be omitted rather than set null — worth documenting. |
| `CREATE (:T {l: [1,2,3]})` | `property 'l' must be a literal value (int, float, bool, or string)` | No list/array properties. Fine, but undocumented. |

### Documentation drift (the actionable part)

The bundled skill docs are out of date in **both** directions:

- Documented as broken, **actually works now**: `CREATE (...) RETURN ...` (returns
  a `"?"` column with `null`, but no longer errors); `CREATE (a)-[:R]->(b)`
  without a preceding `MATCH`.
- Documented as working, **actually broken**: `MATCH (a)-[*1..3]->(b)`;
  `RETURN DISTINCT type(r)`.

Recommend generating the "supported Cypher" doc from the same test suite that
gates releases, so it cannot drift.

## S3 — Ergonomics & packaging

### S3-1. `DISTINCT` fails with the error string `not found`

No context: no clause, no token, no position. Compare with the genuinely good
messages elsewhere (`variable-length paths require a relationship type: use [:R*]
not [*]`). Worth an audit pass for any error that doesn't name what wasn't found.

### S3-2. ESM consumers cannot use the documented import

```js
import { SparrowDB } from 'sparrowdb';
// SyntaxError: Named export 'SparrowDB' not found. The requested module
// 'sparrowdb' is a CommonJS module...
```

`package.json` has `"main": "index.js"` with no `"exports"` map and no ESM
wrapper, so the named import in the `index.d.ts` header example **does not work**
in any `"type": "module"` project. Consumers must write:

```js
import pkg from 'sparrowdb';
const { SparrowDB } = pkg;
```

Zora is pure ESM, as is most modern Node TypeScript. The types promise an import
form the runtime rejects — TypeScript will happily compile the broken form.

**Fix:** add an `"exports"` map with a `.mjs` wrapper re-exporting the named
bindings, and update the doc example. Small change, removes a first-five-minutes
papercut for every ESM consumer.

### S3-3. `execute()` is synchronous — no async variant

Measured on this machine:

| Operation | Time |
|---|---|
| 2000 × `CREATE` (single-node, one call each) | 2209 ms → **~1.1 ms per write** |
| `MATCH (n:Bulk) RETURN n.i` over 2000 nodes | 29 ms |
| `checkpoint()` after 2000 inserts | 2 ms |
| `optimize()` | 4 ms |

Every one of those blocks the Node event loop. For a long-running daemon, ~1.1 ms
per write means a 500-node import stalls the loop for half a second. `checkpoint`
and `optimize` are pleasantly cheap, which is good news.

Zora's workaround is to run the store on a `worker_thread` behind a
message-passing façade — which works, but every consumer will independently build
that.

**Enhancement:** expose async variants via napi-rs `AsyncTask` /
`ThreadsafeFunction` — `executeAsync(cypher, params?)` returning a `Promise`,
running on the libuv threadpool. That plus a `executeBatch(statements[])` (which
would also soften the multi-clause gap in S2) would remove the need for consumer
worker threads entirely.

### S3-4. Platform coverage — better than it looks, worth stating

`optionalDependencies` correctly lists all five targets — `linux-x64-gnu`,
`linux-arm64-gnu`, `darwin-x64`, `darwin-arm64`, `win32-x64-msvc`. Good coverage.

Two notes: there is **no `linux-*-musl` build**, so Alpine-based containers
(extremely common for Node services, and relevant to Zora since it ships a
Dockerfile) will fail to resolve a binary. And it would help consumers if the
failure mode on an unsupported platform were a clear, catchable error naming the
platform rather than a bare module-resolution failure — anything doing optional/
lazy loading needs to distinguish "not installed" from "unsupported here".

### S3-5. Transaction API is published but unusable

`ReadTx.execute()` and `WriteTx.execute()` both throw, pointing at SPA-100 and
SPA-99 respectively. `beginRead()` returns a working `snapshotTxnId` and
`beginWrite()` correctly enforces single-writer (`writer busy: a write
transaction is already active`), so the plumbing is there.

This is already tracked upstream and honestly documented — flagging only because
it's load-bearing for consumers: **no multi-statement atomicity is available
today**, so every consumer must design for idempotent writes and partial-failure
recovery. Worth calling out prominently in the README rather than only in a
doc-comment, since it shapes integration architecture.

## Suggested priority

If the goal is "safe to build a product on":

1. **S0 + S1-1** — parameter binding, and reject unbound `$params` in the
   meantime. Everything else is secondary; this is the one that can lose data or
   leak it.
2. **S1-2** — whole-node return. Currently unusable *and* contradicts the types.
3. **S2 edge mutation + `DETACH DELETE`** — without these a knowledge graph is
   effectively append-only, which is a hard constraint on any real consumer.
4. **S3-2** — ESM export map. Ten-minute fix, unblocks the whole modern Node
   ecosystem.
5. **S1-3, S1-4, S3-1** — type fidelity and error quality.
6. **S3-3** — async API. The highest-leverage *enhancement* once correctness is
   settled, because it deletes a whole category of consumer boilerplate.
7. **S2 doc drift** — generate supported-Cypher docs from the test suite.

## Reproducing

```sh
npm install sparrowdb
node sparrowdb-probe.mjs    # broad capability sweep, ~50 cases
node sparrowdb-probe2.mjs   # injection, type fidelity, timing
```

Both print PASS/FAIL per case and are self-contained (each opens a fresh temp
database). They're structured to be dropped into `node --test` with minimal
editing if you want them as the regression suite.
